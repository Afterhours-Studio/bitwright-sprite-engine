# Internationalization

How translations work here, how to add a string, and how to add a language.

Bitwright ships English (`en`, the default and the fallback) and Vietnamese
(`vi`). Both carry the same set of keys, and CI fails on a mismatch.

## Layout

```
apps/desktop/src/locales/
├── en/
│   ├── common.json      shell, navigation, status, gallery
│   ├── generation.json  the Generate screen
│   ├── settings.json    the Settings screen
│   └── errors.json      reason codes from Rust and Python
└── vi/
    └── (the same four files, the same keys)
```

Four namespaces rather than one file, so that a translator working on Settings
is not merging against changes to error messages.

| Namespace | Holds |
| --- | --- |
| `common` | Anything used on more than one screen |
| `generation` | The Generate screen and its parameters |
| `settings` | The Settings screen, engines, and models |
| `errors` | Reason codes, keyed to match exactly |

Translations are compiled into the bundle rather than fetched. The application
runs offline, and a failed request would leave the interface showing raw keys.

## Using a string

```typescript
import { useTranslation } from 'react-i18next';

export function GenerateButton(): ReactElement {
  const { t } = useTranslation('generation');
  return <button>{t('actions.generate')}</button>;
}
```

Keys are typed from the English files, through `src/types/i18next.d.ts`. A typo
does not compile, and neither does a key from the wrong namespace.

Two namespaces in one component:

```typescript
const { t } = useTranslation('settings');
const { t: tCommon } = useTranslation();
```

Interpolation:

```json
{ "duration": "Took {{ms}} ms" }
```

```typescript
t('result.duration', { ms: 1240 });
```

Plurals use i18next's suffixes:

```json
{
  "count_one": "{{count}} sprite",
  "count_other": "{{count}} sprites"
}
```

```typescript
t('result.count', { count: images.length });
```

Vietnamese has no plural inflection, so both forms are the same text there. Both
keys must still exist; the parity test requires it.

## Adding a string

1. Add the key to the right namespace under `locales/en/`.
2. Add the same key under `locales/vi/`. If you do not speak Vietnamese, copy
   the English text so the key exists, and say so in the pull request
   description. A missing key is a failure; an untranslated one is a follow-up.
3. Use it through `useTranslation`. Never write a literal.
4. Run `npm run test`. The parity test compares the key sets.

Keys are nested and descriptive. `actions.generate`, not `btn1`.

## Error codes

The `errors` namespace is different: its keys are not chosen, they are dictated
by Rust and Python.

Both sides return a stable code rather than a sentence:

```python
class BackendUnavailableError(BackendError):
    code = "backend.unavailable"
```

```rust
#[error("sidecar.startup_timeout")]
StartupTimeout,
```

The code is the translation key. `backend.cuda.driver_missing` becomes:

```json
{
  "backend": {
    "cuda": {
      "driver_missing": "No CUDA driver was found. Install the NVIDIA driver and restart."
    }
  }
}
```

`useErrorMessage` looks the code up and falls back to the generic message when
it has no entry, so an unmapped code never shows the user a raw identifier.

**Adding a reason code in Rust or Python means adding it to both locale files in
the same pull request.** Otherwise the user gets "An unexpected error occurred"
for a failure the code knew the cause of.

## Adding a language

Take Portuguese, `pt`, as the example.

### 1. Copy the namespace files

```bash
cd apps/desktop/src/locales
cp -r en pt
```

Translate the values. Leave the keys alone.

### 2. Register the language

In `src/lib/i18n.ts`:

```typescript
import ptCommon from '@/locales/pt/common.json';
import ptErrors from '@/locales/pt/errors.json';
import ptGeneration from '@/locales/pt/generation.json';
import ptSettings from '@/locales/pt/settings.json';

export const LANGUAGES = ['en', 'vi', 'pt'] as const;

export const resources = {
  en: { /* ... */ },
  vi: { /* ... */ },
  pt: {
    common: ptCommon,
    generation: ptGeneration,
    settings: ptSettings,
    errors: ptErrors,
  },
} as const;
```

### 3. Add the language name

In `common.json`, for every language, under `language`:

```json
{ "language": { "en": "English", "vi": "Vietnamese", "pt": "Portuguese" } }
```

Each file gives the name in its own language.

### 4. Verify

```bash
npm run test
npm run typecheck
```

The parity test now includes the new language, and fails on any key you missed.

### 5. Check it in the application

Run it, switch language in Settings, and look at every screen. Two things go
wrong at this stage:

- **Overflow.** German and Vietnamese run longer than English. A label that fits
  in the parameters panel in English may not.
- **Untranslated strings.** A string that still reads in English was hardcoded
  in a component. Fix the component rather than the locale file.

## Guidelines for translators

- Keep interpolation placeholders exactly as they appear: `{{ms}}`, `{{count}}`.
- Do not translate a product name: Bitwright, CUDA, Metal, LoRA, seed.
- Match the register of the English, which is plain and direct.
- No emoji.
- An error message says what happened and what to do about it. Keep both halves.

## What is not translated

- Source code, comments, and documentation. English throughout.
- Commit messages and pull request descriptions.
- The engine's log output, which is read by developers.
- Model identifiers and licence names.
